# RobViz 双仓库插件化迁移计划

> 状态：已授权执行，当前在隔离 worktree 中进行共享 UI 迁移。
>
> 目标：Core 独立运行，插件独立安装，插件之间没有运行时依赖。

## 1. 最终目标与执行边界

本次改造形成两个公开仓库和一份本地私有插件归档：

| 位置 | 职责 |
| --- | --- |
| `/home/rc4/robviz` | 基础宿主、公开 SDK、插件安装与加载、通用后端 |
| `/home/rc4/robviz_plugins` | 通用插件源码、构建工具、可直接安装的分发目录 |
| `/home/rc4/robviz_fruit_plugins` | 果蔬插件及其私有后端说明，不公开发布 |

本文沿用讨论中后续使用的 `robviz_plugins` 名称。创建远端前确认最终仓库名和归属。

### 1.1 已确定的要求

- Core 保留基础 3D、Foxglove 通信、TF、工作区、多会话和插件宿主。
- URDF、导航、遥控、地图编辑、航点编辑、图像、终端和曲线由插件实现。
- 插件使用 Native ESM，通过 Import Maps 共享宿主运行库。
- GitHub 安装和手动复制最终使用同一个 `plugins/` 目录。
- 插件不能导入其他插件，安装一个插件不能要求先安装另一个插件。
- 公共基础能力由 Core SDK 提供，业务协议不得借共享之名进入 Core。
- UI 样式、通用组件和界面框架由 Core 统一提供，插件不得各自维护一套基础 UI。
- 通用 ROS 2 后端保留在 Core 仓库的 `ros2/`。
- 果蔬插件保持私有，并迁移为新版可安装插件。
- 重构前保存完整旧系统，并创建 `archive/fruit-competition-legacy` 归档分支。

### 1.2 本计划采用的推荐实现

以下是补全执行链路的推荐细节，不冒充此前已经确认的事项：

- 复用现有 HTTP 服务技术，提供最小插件扫描、安装和卸载功能。
- 默认安装目录是 RobViz 服务所在机器的目录，不是浏览器电脑的任意目录。
- 第一版安装、升级和启停后刷新页面，不实现无刷新热卸载。
- 已安装插件可离线使用，不引入浏览器缓存作为第二套安装源。
- 优先复用现有依赖，不增加微前端框架、账号系统或插件沙箱。
- 先完成一个最小插件的生产构建闭环，再批量迁移功能。

### 1.3 非目标

- 不开发第三方市场运营平台、插件付费系统或社区审核平台。
- 不引入插件依赖解析器，也不增加插件之间的调用总线。
- 不在浏览器中编译 TSX，不执行下载包中的安装脚本。
- 不自动安装或启动 ROS 节点，不把下载插件等同于部署机器人后端。
- 不承诺旧配置完全无损迁移，但必须保留旧配置备份和明确迁移说明。
- 不删除业务功能来降低迁移难度。不能保留的功能必须先列明并获得确认。

## 2. Core 与插件的边界

### 2.1 Core 保留内容

| 类别 | 内容 |
| --- | --- |
| 数据通道 | Foxglove 连接、消息解码、订阅、发布、服务调用、断线处理 |
| 坐标与场景 | TF、基础 3D 画布、相机、坐标系、基础消息显示器 |
| 基础显示器 | 点云、LaserScan、TF、Marker、Path、OccupancyGrid 等通用数据显示 |
| 宿主界面 | 话题列表、TF 树、工作区、Dockview、会话、主题、语言、设置 |
| 插件宿主 | 包校验、发现、安装、启停、状态保存、扩展点、错误隔离 |
| 共享基础能力 | 已被实际使用的通用 UI、HTTP 请求、视频客户端、日志显示能力 |
| 通用后端 | 插件文件服务、通用文件 API、视频网关、图像压缩和必要网关服务 |

地图消息显示属于基础显示器。地图编辑和导航控制属于插件。
基础 3D 始终可用，不再通过 `view-3d` 插件控制是否存在。
显示器接口允许插件扩展场景，但不公开整个 `App` 或 `SceneManager` 的内部状态。

### 2.2 官方插件清单

| 插件 | 完整职责 | 后端需求 |
| --- | --- | --- |
| `teleop` | 底盘遥控及其控制策略 | Foxglove 发布 |
| `nav-goals` | 导航目标、初始位姿及视口交互 | Foxglove 发布或机器人提供的接口 |
| `urdf-editor` | URDF 模型加载、显示、关节操作和 XML 编辑 | 本地文件，按现有功能提供可选机器人接口 |
| `map-editor` | 栅格地图编辑、导入、导出和保存 | 本地文件或通用文件 API |
| `waypoints-editor` | 通用航点及背景图编辑、导入、导出和保存 | 本地文件或通用文件 API |
| `image` | 普通图像面板及视频预览 | Foxglove 图像或通用视频网关 |
| `image-capture` | 原始图像预览和无损截图 | 支持截图协议的视频网关 |
| `plot` | 曲线面板和配置 | Foxglove 订阅 |
| `terminal` | 终端页面、连接交互和终端控制 | 独立终端网关 |

`image` 和 `terminal` 补齐原七项清单的遗漏，不新增业务功能。
共享视频客户端或终端渲染组件可以由 SDK 提供，但对应功能入口仍属于插件。

### 2.3 私有插件清单

- `fruit-arm`：机械臂状态、预设、计算预览及相关操作。
- `fruit-competition`：比赛状态、任务控制和比赛监控。
- `fruit-scripts`：项目脚本参数、执行状态和日志。
- `waypoints-maker`：比赛打点、路线预设和项目导航调试。

私有插件使用相同安装格式。Core 不包含这些插件的名称、话题或协议判断。

### 2.4 统一 UI 是宿主契约

插件化拆分的是业务功能，不是设计系统。官方插件和私有插件遵守同一套 UI 契约。
视觉基准固定为现有 3D 主页。已有插件必须改用共享组件，不能只约束未来的新插件。

| 内容 | 归属与规则 |
| --- | --- |
| 颜色、字号、间距、圆角、边框、层级及交互状态 | Core 统一维护设计令牌，插件不得复制或自行定义基础值 |
| 按钮、输入、选择、开关、标签及基础状态提示 | Core 提供共享组件，插件直接使用 |
| 页面容器、工具栏、表单行、操作区、空状态和错误状态 | Core 提供共享组件或明确的通用样式契约 |
| 面板标题、关闭、拖拽、停靠及最大化 | 宿主管理，插件不重复绘制外框 |
| 分栏、日志终端及视频显示等实际复用能力 | Core 提供共享组件，重型依赖按需加载 |
| 机械臂布局、比赛数据和其他业务内容 | 插件实现，但使用 Core 组件和设计令牌 |
| 图表、3D 场景、地图画布等数据表现 | 插件可定义数据配色，外围控件仍遵守统一 UI |

插件只保留业务内容所需的少量局部样式。禁止复制基础按钮、输入框和页面骨架样式。
共享样式随 Core 加载一次，插件包不重复包含宿主设计系统。
共享组件的状态、键盘操作和焦点行为同样由 Core 统一维护。
不直接套用新的 UI 框架，先收敛当前已有样式和组件。
复用频率不能成为把业务组件放入 Core 的理由，业务协议仍留在插件内。

## 3. 仓库与目录

```text
robviz/
├── src/
│   ├── app/                 # 通用宿主与插件管理界面
│   ├── core/                # 数据、配置和通用计算
│   ├── renderers/           # 基础 3D 与通用显示器
│   ├── sdk/                 # 明确的公开导出入口

├── ros2/                    # 通用机器人后端，按需构建和启动

├── scripts/                 # 开发、构建、索引与验证工具
└── docs/

robviz_plugins/
├── src/<plugin-id>/         # 每个插件的完整实现
├── shared/                  # 可选的构建期共享源码，确有复用才添加
```

公共插件仓使用现有包管理器和一个锁文件。第一版不要求为每个插件创建独立 npm 包。
私有插件仓不复制整套 Core，不保留对 Core 内部源码的相对导入。

## 4. 插件包与分发契约

### 4.1 可安装包

```text
plugins/teleop/
├── manifest.json
├── index.js
├── style.css               # 可选
└── assets/                 # 确实需要的静态资源，可选
```

推荐的最小 manifest：

```json
{
  "id": "teleop",
  "name": "Teleop",
  "version": "1.0.0",
  "sdkApiVersion": 1,
  "entry": "index.js",
  "style": "style.css",
  "files": ["index.js", "style.css"],
  "requiredServices": []
}
```

- `sdkApiVersion` 第一版采用整数主版本匹配，不实现复杂版本求解。
- `id` 必须与目录名一致，且只能使用约定的安全字符。
- `entry`、`style` 和 `files` 只能指向包内相对路径。
- `requiredServices` 描述后端能力和协议版本，不声明前端插件依赖。
- `files` 覆盖全部运行资源。GitHub 清单记录包文件及其校验摘要。
- JS 默认导出插件定义。宿主对 manifest 和运行时定义均做形状校验。
- 默认输出一个 ESM 入口，专属依赖打入包，不产生未声明的远程导入。
- CSS 使用插件命名空间，不覆盖宿主全局标签或其他插件样式。
- 包内资源通过模块相对 URL 引用，不能写死 `/src/` 或开发机路径。

### 4.2 GitHub 仓库中的目录必须能直接安装

用户复制 `robviz_plugins/plugins/<id>/` 后应直接可用，不应再要求编译。
因此，该目录作为正式分发文件维护，与源码同时更新并接受审查。
插件仓有意保留这些分发文件，Core 仓不提交用户安装的插件。

发布时从同一份分发目录生成每插件压缩包，并上传 GitHub Release。
`catalog.json` 指向固定版本产物，不使用会悄悄改变内容的 `latest` 入口。
在线安装与手动复制必须使用相同版本、相同文件及相同校验规则。
不要求 GitHub Pages、npm CDN 或独立 npm 发布才能完成第一版分发。

## 5. 安装、发现和加载

### 5.1 只有一个安装事实来源

`plugins/` 是服务端目录。网页应显示实际安装位置和服务所在主机。
浏览器 localStorage 只保存启停、布局和插件配置，不保存插件执行代码。
安装状态由服务端管理，启停和插件状态按现有会话契约保存。

### 5.2 在线安装

1. 用户打开插件管理页，读取官方 GitHub 清单。
2. 用户选择插件，查看版本、兼容性、后端需求和可信代码提示。
3. 安装服务从允许的 GitHub 来源下载固定版本产物。
4. 安装服务在临时目录校验路径、文件、大小、摘要和 SDK 版本。
5. 安装服务在同文件系统内受锁保护地切换目录，并更新已安装清单。
6. 网页提示保存当前工作，确认后刷新并加载插件。

升级失败保留旧包。不能先删除旧版本再下载新版本。
目录切换需要恢复记录或等价保护，不假设能原子覆盖任意非空目录。
网络失败和下载取消不得留下半安装插件，也不得影响已安装插件。

### 5.3 手动安装

1. 用户下载分发目录，或从 GitHub Release 解压插件包。
2. 用户将完整目录复制到服务所在机器的 `plugins/<id>/`。
3. 用户点击重新扫描，或重启服务触发扫描。
4. 服务校验目录，网页列出可启用的插件。
5. 用户确认启用后刷新页面。

不监视文件系统变化，不扫描任意磁盘目录，也不递归加载来源不明的 JS。
服务更新维护的索引，不依赖 HTTP 目录列表功能。

扫描和安装都应按插件 id 拒绝重复记录，并串行处理同一插件的写操作。
加载地址包含安装版本或摘要，避免升级后仍使用旧 JS 或旧 CSS。
文件服务返回正确的 ESM MIME 类型，并限制静态资源访问范围。
开发部署、生产部署和非根路径部署都验证入口及相对资源地址。

### 5.4 纯静态部署

纯静态部署保留加载能力，但没有网页写入服务端目录的能力。
用户手动复制插件，并运行同一校验及索引生成命令后重新部署静态文件。
管理页显示只读安装模式，不把“保存到浏览器缓存”冒充本地安装。

### 5.5 安装服务边界

- 复用现有 HTTP 栈，只添加清单、扫描、安装和卸载所需端点。
- 第一版只允许受配置约束的官方 GitHub 来源，私有插件使用手动复制。
- 默认只在本机开放管理写操作，远程管理可使用 SSH 转发。
- 不因进入私有局域网就自动允许管理写操作。
- 写操作校验 Host、Origin 和请求类型，防止跨站请求及 DNS 重绑定。
- 公开静态服务不默认开放插件安装、文件写入或终端控制。
- 限制下载大小、解压大小、文件数量、超时和重定向目的地。
- 拒绝绝对路径、目录穿越、符号链接和越界资源。
- 不接受任意 URL 作为后端下载代理，不执行插件附带命令。
- GitHub 凭据不进入前端配置、导出文件、下载目录或日志。

## 6. SDK 与零跨插件依赖

### 6.1 依赖方向

```text
插件 → @robviz/core 公开 SDK
插件 → 宿主共享运行库
插件 → 自身打包的业务代码及第三方依赖

禁止：插件 A → 插件 B
禁止：插件 → Core 内部源码路径
禁止：Core → 某个具体功能插件
```

插件仓内部可以复用业务源码，但构建后每个插件都包含自己所需的代码。
构建期共享不应形成运行时共享文件依赖，更不能要求先安装另一插件。
少量重复代码可以接受，不能为去重把果蔬业务协议搬入 SDK。

### 6.2 SDK 初始公开能力

| 能力 | 约定 |
| --- | --- |
| 插件类型 | 插件定义、页面、面板、区块、显示器、视口工具和服务声明 |
| 通信 | 复用现有 bridge，暴露迁移需要的稳定方法与类型 |
| TF | 查询接口、坐标类型及已有通用计算 |
| 宿主上下文 | 主题、语言、连接状态、活动会话、话题、固定坐标系 |
| 插件状态 | 仅访问自身状态，宿主负责持久化和配置导入导出 |
| 服务地址 | 复用 getServiceUrl 和会话地址覆盖，不写死机器人主机 |
| HTTP | 复用通用请求、取消、超时和明确错误处理，不包含业务 schema |
| 通用 UI | 优先导出现有输入组件和样式令牌，再按实际需求补充 |
| 可选共享媒体 | 复用视频客户端和日志终端渲染，依赖按需加载 |

不预先创建未使用的 `Toast`、`Dialog` 或全新表单框架。
不为了命名统一而为每个现有对象增加一层包装类。
插件不能通过公开上下文读取或修改其他插件状态。
保留稳定的面板 kind 和插件 id，避免迁移时无故重置布局。

Core 同时生成 SDK 类型声明及最小开发包，供插件仓独立安装和类型检查。
第一版可以使用本地打包产物，不要求先发布到 npm。
类型检查时解析开发包，运行时由宿主 Import Map 解析同一公开入口。
发布插件时记录构建使用的 SDK 版本，禁止依赖临时文件系统软链接才能构建。

### 6.3 消息 schema 与 3D 扩展

目前发布类型受固定 `PUB_SCHEMAS` 限制。实施时核对全部插件实际需要。
需要扩展类型时，由插件声明 schema，宿主验证并注册到现有通信链路。
不能每增加一个业务类型，就修改 Core 的固定类型表。
相同类型的冲突定义必须拒绝，不能按加载顺序静默覆盖。

3D 扩展优先使用现有显示器接口和视口工具。
URDF 在主视口确需模型挂载能力时，只补最小挂载及释放接口。
插件自有编辑场景仍由插件管理，不把编辑器业务加入基础 3D。

### 6.4 ESM 共享运行库

- 宿主与插件统一解析到同一份 React 和 React DOM。
- 显式覆盖实际使用的 `react/jsx-runtime` 等子路径。
- Three.js 需要跨边界共享时使用相同模块实例。
- Import Map 必须在相关模块加载前建立。
- 共享运行库随 Core 本地分发，不在离线启动时请求公网 CDN。
- 插件构建 external 公开 SDK 和约定运行库，其他依赖默认自身打包。
- 不通过 Import Map 指向另一插件的模块。

不能仅检查插件 bundle 中没有 React，还要验证宿主没有另用第二份实例。
第一阶段技术验证必须覆盖开发模式与生产构建。

### 6.5 共享 UI 的迁移顺序

1. 盘点现有页面中重复的控件、布局、样式和交互行为。
2. 在 Core 中收敛已有组件和设计令牌，确定公开的 UI 导出入口。
3. 优先提供插件迁移实际使用的控件与布局，不提前建设未使用的组件库。
4. 将通用终端、分栏、状态和媒体展示从业务页面中分离。
5. 迁移插件时改用共享 UI，删除对应的重复基础样式。
6. 在相同主题、字号和窗口尺寸下对照检查所有插件。

插件通过 `@robviz/core` 使用共享 UI，不依赖某个“UI 插件”。
宿主与插件使用同一份组件实现，不能只是拷贝看起来相似的组件。

## 7. 生命周期、错误和状态

- 第一版采用“保存提示、刷新生效”，不实现 ESM 真正卸载。
- 禁用插件后不导入其入口。模块顶层仍禁止创建连接和订阅。
- 订阅、定时器、DOM 监听、视口对象和媒体连接必须清理。
- 面板、页面和显示器按现有机制隔离错误，并显示插件 id 与错误原因。
- 一个插件加载失败，其他插件和基础 3D 继续运行。
- 缺失后端只禁用相关操作，不导致插件安装失败或宿主崩溃。
- 断线后的发布和服务请求必须快速失败，不能在重连后补发旧动作。
- 插件负责活动会话之外的控制策略，Core 不引入统一后台控制策略。
- 未安装或禁用插件时保留其布局和状态，重新安装后允许恢复。
- 配置导入只恢复数据，不自动下载、信任或执行配置中提到的插件。
- 刷新或禁用前提示未保存内容，不自动清空整个 Dockview 布局。
- 插件管理和迁移界面保留键盘操作、控件标签、焦点管理及可读的错误提示。

原生 ESM 插件是可信代码，不是沙箱。manifest 能力声明不等于权限隔离。
第一版只运行用户明确安装的可信插件，不承诺能够安全执行恶意插件。

## 8. 后端拆分

### 8.1 通用后端

在 `robviz/ros2/` 保留已有通用视频网关和图像压缩器。
从 `fruit_robviz_bridge` 提取确实需要的通用 Web、文件及图像设置能力。
非 ROS 服务不为目录统一而强制包装成 ROS 节点。
终端网关继续使用现有独立实现，不因共享终端 UI 而默认启动。

通用文件 API 必须保留：

- 可访问文件范围限制。
- 输入格式与大小校验。
- 文件版本冲突检测。
- 备份和原子写入。
- 写入失败时保留原文件。

视频后端保持无客户端时不启动编码等已有资源策略。
截图保存目录改为明确配置，不保留 `/home/rc4/fruit_ws` 硬编码。
各后端按功能需要启动，Core 基础 3D 不要求视频、终端或文件服务存在。

### 8.2 私有后端

以下内容保留在 `fruit_ws` 或私有归档，不进入 Core：

- 机械臂计算、预设和硬件接口适配。
- 果蔬检测、二维码融合和坐标投影。
- 比赛流程、路线模板、任务清单和项目启动脚本。
- 对 fruit_interfaces、fruit_arm_planner 等业务包的依赖。

私有 README 列出源码位置、配置、构建方式和接口版本。
前端插件独立安装不意味着私有后端自动可用。
真实机械臂操作继续通过 planner API，不能为恢复插件而绕过原安全边界。

## 9. 分阶段执行

阶段依赖：`P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7`。
每阶段先通过完成条件，再清理对应旧实现。不要先删除再补迁移。

### P0：保存旧系统与建立功能清单

任务：

1. 核对 Core、fruit_ws、相关分支、工作区及本地未提交修改。
2. 保存已提交基线，并创建约定的归档分支，不覆盖同名分支。
3. 单独保存未提交差异、暂存差异和任务相关未跟踪文件。
4. 记录依赖锁文件、部署方式、配置路径和私有后端版本。
5. 为全部现有入口建立“功能 → 实现 → 依赖 → 目标插件”清单。
6. 记录旧配置样本，并将凭据、运行日志和数据集排除在公开资产之外。

交付物：旧系统恢复说明、功能迁移清单、备份位置。

完成条件：能够恢复旧前端及其后端配置，而不只恢复四个插件目录。
复杂重构采用隔离 worktree，验收后再按工程规则合并 main。
计划和文档交付不要求创建 worktree，重构执行时才创建。

### P1：确定最小契约与 SDK

任务：

1. 定义 manifest、SDK 主版本和运行时插件定义的校验规则。
2. 建立公开 SDK 入口，先导出现有可复用实现。
   同时收敛公共 UI 样式、控件和页面骨架，作为后续插件迁移的前置条件。
3. 明确共享运行库、状态归属、服务声明和插件资源规则。
4. 让基础 3D 不依赖 `view-3d` 插件，同时保留旧配置数据。
5. 记录所有待迁移的 Core 专属字段和跨插件导入。
6. 明确 GitHub 官方来源、安装根目录和服务写操作边界。

交付物：插件契约、SDK 入口、最小插件模板和构建配置。

完成条件：模板只通过公开 SDK 编译，不引用 Core 内部目录。

### P2：用 teleop 验证端到端链路

任务：

1. 建立 `robviz_plugins` 本地仓库和最小统一构建工具。
2. 将 teleop 的完整实现迁入插件仓，生成分发目录。
3. 接入 Native ESM 加载和共享运行库。
4. 加入安装服务、目录扫描和插件管理最小界面。
5. 先验证手动复制，再用受控 GitHub 版本产物验证在线安装。
6. 验证启停、刷新、配置恢复、错误提示和离线重启。
7. 验证断线快速失败，不连接真实硬件进行危险控制检查。

交付物：Core 加载器、安装闭环、独立 teleop 包。

完成条件：生产构建安装插件不需要重建 Core，React 不出现双实例问题。
若 ESM 单例或资源路径未通过验证，停止批量迁移并修正基础链路。

### P3：迁移通用功能插件

按低耦合到高耦合顺序迁移：

1. `nav-goals`。
2. `plot`。
3. `terminal`。
4. `urdf-editor`。
5. `map-editor`。
6. `waypoints-editor`。
7. `image` 和 `image-capture`。

每个插件执行同一组任务：

- 移动完整实现、专属样式、资源和依赖，不只移动入口。
- 使用 Core 的共享 UI 和设计令牌，不把重复基础样式一起搬进插件。
- 保留现有用户功能和交互，使用功能清单逐项核对。
- 移除 App.tsx 的专属导入与业务分支，改由扩展点承载。
- 将专属配置归入插件状态，提供必要的旧字段迁移。
- 单独安装该插件，验证没有其他功能插件仍可工作。
- 检查生产分发目录不引用源码路径或外部插件文件。
- 通过该项验收后，删除 Core 中对应旧实现及不再需要的专属依赖。

交付物：九个独立官方插件及对应迁移记录。

完成条件：Core 不依赖插件源码，功能清单没有未解释的缺项。

### P4：迁移并通用化后端

任务：

1. 核对官方插件实际使用的全部后端接口。
2. 将通用文件、图像设置和静态服务从果蔬业务中分离。
3. 核对已有通用视频网关与果蔬版本差异，保留通用所需能力。
4. 替换项目路径、固定话题和服务名，使用明确配置及服务发现。
5. 保留文件冲突、备份、输入校验和安全写入保护。
6. 为每项后端能力提供最小启动说明和协议版本说明。
7. 验证在不构建 fruit_ws 业务包的环境中运行通用链路。

P3 中需要后端才能验收的插件，先复用旧服务验证界面，再在本阶段完成独立验收。
旧服务只能作为迁移中的临时依赖，不能作为最终交付前提。

交付物：Core 仓内通用后端、配置示例和前后端接口表。

完成条件：官方插件不需要 fruit_interfaces 或 fruit_arm_planner 等业务包。

### P5：迁移私有插件

任务：

1. 将四个私有插件迁入 `robviz_fruit_plugins`。
2. 将通用请求函数迁入 SDK，将比赛协议保留在私有代码中。
3. 消除 fruit-arm、fruit-scripts 和 fruit-competition 之间的导入。
4. 对确需复用的私有协议源码，在构建时分别打入各插件。
5. 使用 SDK 的共享图像、日志或终端组件，不依赖对应前端插件。
6. 生成可直接复制安装的私有分发目录。
7. 记录私有后端的恢复方式并验证已有只读能力。

交付物：四个可安装私有插件、后端要求和恢复说明。

完成条件：每个私有插件可单独加载，缺少其他私有插件不影响自身入口。
涉及真实机器人动作的检查需要操作人员确认，不能由“比赛结束”推导出运动授权。

### P6：Core 提纯与状态迁移

任务：

1. 清除源码、默认配置和文案中的果蔬业务硬编码。
2. 移除对具体插件的启用判断、页面分支和专属样式。
3. 将 urdfInspectorPercent 等专属字段迁入对应插件状态。
4. 保留旧配置备份，对无法迁移的字段提供明确说明。
5. 保留未安装插件的状态，避免加载一次 Core 就抹除用户配置。
6. 检查空 plugins/ 下的启动、连接、基础显示和配置导出。
7. 将默认视频和终端服务配置调整为可选能力，不强制启动。

交付物：不含业务插件实现的 Core、配置迁移说明和空插件演示。

完成条件：不存在为了某个功能插件而保留的宿主业务判断。

### P7：发布与交付

任务：

1. 更新 Core README、插件开发指南、安装说明和故障处理说明。
2. 更新插件仓清单、构建说明、每插件后端要求和许可证声明。
3. 核对分发文件、源码版本、摘要和 Release 版本一致。
4. 在干净目录完成 Core 构建与插件单独构建。
5. 分别验证手动复制、GitHub 安装和离线重启。
6. 检查公开资产不包含私有插件、凭据、个人绝对路径和业务配置。
7. 汇总验收结果，再执行 main 合并和正式发布。

GitHub 仓库创建、可见性设置和正式发布需获得明确授权。
开发过程使用本地仓库和测试产物，不默认向远端推送。

交付物：两个可发布仓库、私有插件归档、验收记录和恢复说明。

完成条件：第 10 节全部必选项通过，未通过项不能用“后续完善”代替。

## 10. 验收矩阵

| 场景 | 必须满足 |
| --- | --- |
| 空插件目录 | Core 启动，3D、连接、TF 和工作区可用 |
| 单独安装 | 每个官方插件均能独立加载，不请求其他插件文件 |
| 手动复制 | 扫描后识别，不重建 Core |
| GitHub 安装 | 校验后落盘到同一 plugins/，刷新可用 |
| 离线重启 | 已安装插件不依赖 GitHub 或公网 CDN |
| 生产构建 | React Hooks、共享库、CSS 和资源路径正常 |
| 安装失败 | 旧包、已安装清单和运行状态不被破坏 |
| 不兼容包 | 明确拒绝并提示 SDK 版本，不影响 Core |
| 非法路径 | 拒绝越界文件、符号链接和危险解压路径 |
| 缺少后端 | 显示缺失能力，禁用相关操作，页面不崩溃 |
| 连接断开 | 发布与服务快速失败，重连不补发旧控制 |
| 插件异常 | 基础 3D 和其他插件继续运行 |
| 禁用与卸载 | 保留可恢复状态，不静默删除未保存数据 |
| 配置导入 | 不自动下载或执行未知插件 |
| 文件冲突 | 返回冲突，不覆盖其他进程的新文件 |
| 私有插件 | 单独安装，无跨插件导入，不进入公开分发 |
| 统一 UI | 所有插件共用 Core 的组件和基础样式，深浅主题、字号及交互状态一致 |
| 新环境 | 通用功能不需要 fruit_ws 业务包 |

验证方式：

- 对已有数学算法、坐标转换和通信协议运行相关检查。
- 对 manifest、版本、下载和文件服务协议保留最小可运行检查。
- 验证依赖边界时使用真实独立构建和加载，不写 AST 字符串匹配测试。
- 界面生命周期、布局和样式使用小型演示及明确人工检查清单。
- 不增加递归仓库检查器、私有方法模拟或硬编码比赛流程测试。
- 每阶段运行受影响文件的检查，以及现有相关测试，不修复无关问题。
- 所有检查记录命令、环境、结果和未验证边界。
- 不把未连接真实硬件的验证描述成机器人动作已经安全验收。

## 11. 风险与停止条件

| 风险 | 处理与停止条件 |
| --- | --- |
| ESM 共享失败 | P2 停止，不继续批量拆插件 |
| 功能实现遗漏 | 对照 P0 清单补齐，不用删除代替迁移 |
| SDK 持续膨胀 | 业务代码留在插件，允许少量打包重复 |
| GitHub 不可达 | 已安装插件继续运行，提供手动复制流程 |
| 旧配置不兼容 | 保留备份和插件状态，明确迁移限制 |
| 安装过程中断 | 根据恢复记录恢复旧包，不清空整个安装目录 |
| 后端仍依赖果蔬包 | 不标记官方插件独立验收通过 |
| 私有资产公开 | 停止发布，重新核对源码、产物及 Git 历史策略 |

公开之前必须检查仓库历史。删除当前文件不能抹除历史中的私有内容。
如果历史中存在不应公开的内容，先确认历史清理或新建发布仓库策略，不擅自改写历史。

## 12. 执行授权与最终完成定义

本计划不授权立即创建分支、覆盖文件、初始化远端或发布代码。
确认后从 P0 开始。复杂重构按项目规则使用隔离 worktree。
保留已有修改，只暂存任务文件，不做批量 Git 暂存或破坏性清理。
提交与合并按执行时明确授权和适用工程规则进行。

最终完成必须同时满足：

1. Core 不安装插件仍是可用的基础机器人可视化宿主。
2. 安装任意插件不需要其他插件，也不需要重新构建 Core。
3. 官方插件只依赖公开 SDK、共享运行库和自身打包代码。
4. 通用后端不依赖果蔬业务包，私有功能不进入公开 Core。
5. GitHub 安装与手动复制使用相同分发目录和校验规则。
6. 已安装插件可以离线恢复，旧系统具备可执行的恢复说明。
7. 全部已有功能有明确去向，全部必选验收有记录。

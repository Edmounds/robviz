# RobViz Base Platform: Implementation Plan

Status: design agreed; implementation NOT started. This document is for a follow-up coding agent. Read the repository's `AGENTS.md` first. Do not overwrite the current uncommitted edits in `README.md`, `src/app/App.tsx`, `src/app/i18n.tsx`, `src/core/appConfig.ts`, or `tests/unit/appConfig.test.ts`.

## 1. Product Boundary and Decisions

RobViz is a single-user ROS 2 visualization/interaction base. The host owns connection lifecycle, message transport, rendering/workspace, configuration, extension contracts, and fault isolation. Users and plugins own robot-specific topic choices, command semantics, and control policy. Do not turn this work into a general robot safety framework or add robot-specific defaults to core.

Agreed scope:

- Move built-in Teleop and the 3D viewport's Nav Goal/Initial Pose tool into bundled plugins, enabled by default. Keep the schema-driven Service UI in the host. The Nav interaction must remain in the 3D viewport via a minimal viewport-tool plugin extension point, not become only a dock panel. Nav topic names must be editable plugin defaults (`/goal_pose`, `/initialpose`); keep the frame based on the selected fixed frame unless the plugin exposes an override.
- The host does **not** enforce an inactive-machine publish policy. This explicitly supersedes the earlier request that inactive machines never receive speed commands. The Teleop plugin itself pauses when its tab loses focus, clears held input, and requires explicit re-enabling on return. Other plugins own their own background behavior. The host may provide `active` as metadata, not as a universal write guard. Do not claim switching tabs guarantees a remote stop: already-sent messages cannot be recalled, and robot-side timeout is outside this project's control.
- When a page session's Foxglove connection is not open, all page-originated robot writes (`publish`, `callService`) must fail promptly, including plugin calls. Pending service calls reject on disconnect, manual reconnect, Worker failure, or disposal; never replay writes after reconnect. Keep offline file and workspace editing available.
- One bad channel schema/encoding must not crash the Worker or break other topics. Report its failure once for that channel incarnation, quarantine it until the server re-advertises it, then allow a fresh attempt.
- Support double-click rename of machine tabs, showing user name primarily and connection hostname secondarily. Names persist in local/file configuration. Browser `localStorage` remains the auto-restore source; explicit JSON export/import remains the portable backup. Do not include SSH credentials in exported workspace config, and leave the current single-user SSH password storage policy untouched.
- This is a pre-release development project. Do not build a compatibility migration for old Teleop panel kinds/layouts. Configurations use v3 format (`robviz.layout.v3`) and strictly reject legacy v1/v2 files. Do not automatically delete old localStorage or imported files: an obsolete panel may appear as unknown and the user can remove/reset it.

## 2. Current Implementation Facts

- `src/app/App.tsx` directly renders `TeleopSection` and `ServiceSection`, and contains the Nav toolbar, pointer handling, `/goal_pose` and `/initialpose` publishing. Teleop is **not** currently a plugin. `src/plugins/example-odom-hud/index.tsx` is the existing example plugin.
- `src/plugins/types.ts` and `src/plugins/registry.ts` currently expose only `displays`, `panels`, and `sections`. `PluginContext` has a `WorkerBridge` but no active/connection-state metadata. Plugins are discovered via eager `import.meta.glob` and toggled in Settings.
- All machine sessions stay mounted when inactive. `WorkerBridge.setStreamingActive` pauses subscriptions, not publishing. `TeleopSection` currently has a 100 ms publishing timer and a zero-velocity cleanup send; hidden tabs do not unmount it.
- `FoxgloveConnection` clears channels/services on close but does not notify the UI with empty lists. `WorkerBridge` keeps separate pending service promises and only rejects them on Worker error, not connection close/dispose. Worker-side `callService` uses optional chaining when `conn` is absent, producing no response.
- `#readerFor(channel)` executes before the decoder's `try` in `FoxgloveConnection`. `new WebSocket(url)` can throw synchronously for an invalid URL and trigger the Worker restart loop. Manual URL changes also leave stale topic, TF, and cached frame data to consider.
- Existing test commands are `npm test`, `npm run lint`, and `npm run build`. At review time 26 files / 112 tests passed; build and lint passed. Vitest printed a post-test process-exit warning, and the main bundle exceeded 500 kB. Neither is a reason to expand this plan into unrelated performance work.

## 3. Execution Order

### Phase A: Connection and Write Semantics (host)

1. Add a small, testable connection-target validation step before constructing a browser WebSocket. Invalid `ws:`/`wss:` URLs must show one actionable error and leave the Worker alive; do not enter restart/backoff loops for deterministic input errors. Validate loaded session URLs before initiating connection as well as edited ones.
2. Make the connection state transition authoritative in `WorkerBridge`: on manual connect, closed state, Worker failure, and dispose, reject and remove all pending service calls, clear stale topics/services/stats as applicable, recycle/clear queued transferable frames, and notify UI subscribers. Protect against delayed events from the old connection overwriting the new one (connection generation/identity or equivalent). Keep automatic reconnect for genuine transport failures.
3. Gate `WorkerBridge.publish` and `callService` on an actually open connection. `publish` should synchronously reject a disconnected write in a way its caller can handle; `callService` should reject its Promise. Keep a bounded request timeout on the main-thread side so every request settles even if Worker messages are lost; clear timeout on settle. Worker-side `callService` must always return a failed `serviceResult` when no connection exists. Never queue or replay writes. Keep worker publish failures observable, rather than silently treating an asynchronously failed write as delivered.
4. On disconnect, have `FoxgloveConnection` notify `onChannels([])` / `onServices([])` in addition to state changes; ensure the UI disables service submit and plugin control affordances while disconnected, while layout, settings, local PCD/PGM/YAML editing, and JSON import/export remain usable. Clear per-connection TF state when changing to a different URL; do not display old machine transforms as current. A reconnect to the same machine should restore desired subscriptions without duplicating handlers.
5. Add focused tests for invalid URL, disconnect during an in-flight service call, call when disconnected, manual reconnect with a late old response, Worker failure/dispose, cleared lists, and write/no-replay behavior. Tests should cover both `FoxgloveConnection` and `WorkerBridge`, plus the Service UI disabled state.

Acceptance: offline and reconnecting sessions cannot issue new page robot writes; an in-flight service call always settles; stale services do not remain callable; invalid URLs do not restart the Worker indefinitely; unrelated offline editing still works.

### Phase B: Bad Topic Isolation

1. Move channel reader creation/encoding/schema parsing into the per-message guarded path in `FoxgloveConnection`. Distinguish channel-definition failure from a single corrupt data frame. For an invalid channel definition, quarantine by channel ID (or equivalent channel incarnation), report one error, and skip only that channel's messages until unadvertise/re-advertise. Clear quarantine and cached reader when a replacement channel is advertised. Do not repeatedly parse/report on every incoming message.
2. Guard subscription setup and other synchronous protocol callbacks where malformed advertised metadata can throw. Preserve healthy channels, services, and heartbeat; do not mask connection-level failures by treating every fault as a bad topic. Keep malformed payload behavior isolated per frame without turning it into an unbounded log stream.
3. Test two simultaneous channels: malformed schema or unsupported encoding on A, valid messages on B before and after A's failure, no repeated error for A, then A's new advertisement followed by recovery. Include a Worker-level regression if the existing test harness can exercise it without introducing a browser dependency.

Acceptance: a bad channel generates one visible diagnostic per incarnation, does not terminate/restart the Worker, and is retried after re-advertisement.

### Phase C: Plugin Contract and Bundled Controls

1. Extend the smallest necessary plugin surface in `src/plugins/types.ts` / `registry.ts`: expose read-only `active` and connection state to each session's plugins, and define an optional viewport-tool contribution for 3D toolbar actions plus pointer interaction. Keep viewport hit-testing/camera projection in the host; expose normalized ground coordinates and the selected fixed frame to tools instead of giving a plugin unrestricted SceneManager internals. Mount/unmount and disable viewport contributions using the same enabled-plugin registry as panels/sections. Retain the existing ErrorBoundary and display fault isolation behavior.
2. Plan one generic per-session plugin-state path for viewport tool settings if the existing panel-state mechanism cannot serve both the toolbar and its configuration UI. Keep topic choices persisted with the machine session in local/file JSON; avoid a separate untracked localStorage key. Validate imported plugin state at the plugin boundary; it is currently `unknown` in the host schema.
3. Move `src/panels/TeleopSection.tsx` behavior to a bundled Teleop plugin using existing `sections` or a single-instance panel. Supply session `active` metadata, not a global inactive write guard. On loss of active tab or connection, cancel its timer/input listeners, clear held keys/button state, and reset enabled state; switching back requires the user to enable it again. Send a zero command only on an explicit disable while the connection is open and this plugin is active, as a best-effort local behavior; never publish from an inactive cleanup or promise remote delivery. Ensure keyboard shortcuts do not fire while typing or while the tab is inactive. Cover pointer cancel/blur so a released control cannot remain held.
4. Move Nav Goal/Initial Pose topic-specific toolbar buttons, pose/covariance construction, and publishing into a bundled Nav plugin using the viewport extension. Preserve viewport click-position / drag-orientation interaction and existing default topics; expose editable topic settings. Cancel selection cleanly on disconnect, tab switch, plugin disable, or viewport unmount. Keep camera navigation, grid, fixed-frame selection, and generic viewport rendering in the host. Disable publishing UI when connection is not open.
5. Remove only the superseded built-in Teleop/Nav render and publish paths from `App.tsx`, the built-in Teleop entry in `DEFAULT_CORE_PANELS` / default menu, and any obsolete i18n strings. Make both plugins bundled and enabled by default, with ordinary Settings toggles. Fresh workspaces should show the Teleop contribution; disabling a plugin removes its UI and effects. Do not migrate old panel IDs or automatically rewrite saved layouts. Recheck section auto-add behavior so toggling a plugin off/on does not create duplicates or lose a closed section unexpectedly.
6. Add tests for plugin registry/toggles, plugin state restoration, Teleop timer/key cleanup on inactive/disconnected/unmount, no background publishes, explicit re-enable, and Nav viewport coordinate/publish behavior. Include at least one real browser/manual smoke run for a two-tab switch and a disabled plugin; unit tests alone cannot establish keyboard/pointer interaction correctness.

Acceptance: fresh installs retain the familiar Teleop and in-viewport Nav workflows, but robot-specific publishing is implemented in plugins. Session inactivity is available as metadata; the built-in Teleop plugin stops itself, without imposing a host policy on third-party plugins.

### Phase D: Session Tabs and Configuration

1. In `src/app/App.tsx`, show the persisted session `name` as the primary tab text and `connectionTargetLabel(url)` as secondary text (or tooltip when space is tight). Implement double-click rename with an input; Enter/blur commits a trimmed nonempty name, Escape cancels. Prevent the close button or tab selection from swallowing edit events. Provide an accessible keyboard path and label for renaming, and keep small-screen layout stable.
2. Preserve name and per-session plugin settings on immediate browser save, debounced auto-save, file export, and file import. Do not alter the current five uncommitted user edits implementing the browser-save/file-export split except where a focused integration change is needed.
3. Test rename commit/cancel/empty-name behavior, persistence round-trip, primary/secondary label fallback for invalid or incomplete URLs, and two-tab independence. Test fresh default layout without relying on old Teleop IDs; document manual removal/reset of obsolete pre-release layouts. Update `README.md` and plugin guide for current behavior. The execution plan and technical design contain historical claims such as 'no plugin system'; revise only the now-misleading current guidance, not the history of completed milestones.

Acceptance: user-facing tab name is editable and survives reload/export/import; hostname remains visible; saving a fresh workspace round-trips the enabled bundled plugins and their settings.

## 4. Final Verification and Handoff

- Run `npm run lint`, `npm test`, `npm run build`, and `git diff --check`. Capture exact failures if any. Investigate the Vitest exit warning if it persists after related test changes; do not leave a test process running.
- Browser smoke checklist: two sessions connected; toggle Teleop, hold and release a direction, switch away/back; disconnect mid-service-call; invalid URL; bad advertised topic alongside healthy topic; disable/re-enable both bundled plugins; edit and export/import a renamed workspace; confirm offline PCD/map editing still works. Use a simulated bridge for command assertions before any real robot test.
- Explicitly distinguish guarantees: browser host refuses writes while disconnected and does not replay them; the bundled Teleop plugin stops on inactivity. No claim of universal inactive-tab write blocking, guaranteed delivery of stop commands, robot-side watchdog, or safety policy for user plugins.
- Leave SSH credential handling and unrelated ROS packages, performance optimization, and untouched modules alone. Preserve all pre-existing worktree changes and report any tests or robot-side checks that could not be performed.
